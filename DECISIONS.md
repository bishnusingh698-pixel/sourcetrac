# Decisions taken while fixing BUGS.md

Each entry: the bug, what was chosen, and why. Shopify documentation decides
first; otherwise the option safest for merchants and their data.

- **C1** (backfill Option id collision): the already-shipped migration is edited in place rather than adding a new one, because a database with 2+ shops can never have applied it; `prisma migrate deploy` ignores the checksum change on single-shop databases that did apply it (verified locally). Backfilled option ids become `bf-option-<shop>-<channel>`.
- **M1** (stale hidden answers): the server now drops answers to questions hidden by show-if instead of refusing the whole set, and the extension evaluates visibility in order like the server. Chosen because "never lose the answer" outweighs strictness on a field the buyer can no longer see.
- **M4** (one order answered twice): one answer set per order across all surveys, enforced with a per-order Postgres advisory lock inside the submit transaction, matching the existing `alreadyAnswered` rule. No new unique index, so no migration can fail on rows already duplicated in production.
- **M6** (edit/publish while a buyer is answering): archived options remain valid answers, and a submit carrying an older `surveyVersion` is not refused for `required` or for questions that no longer exist; every other rule still applies. The buyer's version is stored on the Response.
- **M7** (id-less submissions): Thank-you and Order-status submissions must carry an order id; id-less placements (on-site/link, behind feature flags) always go through the shop-wide backstop with no known-order exemption.
- **M3/L10** (token cap): the per-token cap now counts only stored answers, so failed attempts and backstop 429s before the order lands no longer lock a real buyer out of their own retries.
- **L11/L12/L39** (half-processed submits): the usage claim, insert and survey count are one transaction; a usage failure fails the request (the extension retries) instead of storing an uncounted, unflagged answer.
- **M19** (submit waits on Shopify): the inline sync now runs in the background, limited to the new response's rows; the buyer's response no longer waits on Shopify.
- **L17** (first-order targeting on Order-status): kept strict. The Order-status page has no first-order signal, and showing a first-order-only survey to an unknown buyer would put the wrong audience into the merchant's data; the misleading "rule stays inert" comments were corrected instead.
- **L18** (any order id can be answered): survey status and placement are now checked. Binding the order id to the token is not possible: Shopify's checkout session token carries no order claim.
- **C5** (template ids): rows keep unique database ids and remember the template's stable id in a new nullable `templateKey` column (additive migration); show-if, the channel report question and duplicated surveys are remapped from posted ids to saved ids. Storing stable ids as row ids was rejected because they collide on the global primary key.
- **H11** (archived rows come back): the Studio no longer receives archived questions/options, and an archived row that is posted back stays archived. Results still read them for their "(removed)" labels.
- **H14** (duplicate): a duplicate copies the *published* survey (what buyers see), not an unpublished draft, and now carries template provenance, design, rotation and learn-and-stop.
- **M23** (equal priorities): ties break on creation order (oldest first), so the winner is stable and matches the list order; new surveys still start at priority 0.
- **M26** (status from a save): a Studio save never changes status or priority; status goes through Activate/Pause (with their guards) and priority through reordering. Publishing a live survey with no placement is refused rather than silently showing nowhere.
- **M28** (editing answered questions): changing the *type* of a question that has answers is refused; relabelling options stays allowed so typos can be fixed.
- **I25** (missing revision): the Studio route now refuses a post without a revision (shown as a conflict). The library functions keep the optional parameter for internal callers, but the check is now an atomic conditional update.
- **L60** (setup wizard): a launch creates the survey as active in the same transaction as the create, so a retry cannot leave a duplicate.
- **C4** (reports read only the legacy table): the dashboard and export now read one union of legacy `SurveyResponse` rows the migration did not copy and every v2 `Response` that answered its survey's channel-report question; migrated `bf-option-<shop>-<value>` ids are folded back to their legacy value so history stays one channel. Answers without an order id (on-site/link) are left out of this order-level report.
- **M33** (rate over 100%): the rate's numerator is now "eligible orders placed in the window that have an answer", the same population as the denominator.
- **M34** (multi-choice revenue): kept full credit per chosen option (splitting an order's value would invent a model the merchant never chose) and added a note under every multiple-choice breakdown saying the amounts can exceed the total.
- **M30/L69** (large result sets): Results aggregates the newest 5,000 answers and says so when capped; both CSVs cap at 50,000 newest rows, read one extra row to detect truncation exactly, send `X-SourceTrac-Truncated`, and the Export page now warns.
- **L73** (Home numbers): an NPS question shows its NPS score; the confidence badge shows the number of answers the label was computed from.
- **L21** (same-second updates): added a nullable `OrderCache.triggeredAt` (additive migration) holding the delivery's `X-Shopify-Triggered-At`; within one second of `updated_at` the later delivery wins. The API backfill, which reads the order's current state, keeps the old "same second applies" rule.
- **L23** (fractional zero-decimal totals): up to two fractional digits on a zero-decimal currency (e.g. ISK "1990.50") are rounded half-up to the whole unit instead of rejecting the order, which left its revenue Pending forever. Other over-precise values are still rejected.
- **M31** (admin pages wait on Shopify): the order backfill now runs in the background with one run per shop at a time; an answer it resolves shows on the next page load instead of the page waiting up to minutes.
- **L24** (backfill retries forever): an order Shopify reports as missing or out of the `read_orders` window waits a week before the next attempt (in memory); throttles and 5xx still retry hourly.
- **M16** (checkout tokens accepted by the admin endpoint): the hand-rolled ID-token check now also requires `iss` = `https://<dest>/admin` and an `exp`, and the endpoint is rate limited per shop. Moving the endpoint onto the library's `authenticate.admin` was not done here because it changes the auth path of a live surface beyond the bug's scope.
- **L44/L45** (buyer text in tags, internal ids in Flow): tags and Flow's `Channel` use a readable key (legacy value, template option key, or a slug of the label); a free-text "Other" answer is the channel `other`, and its text only reaches Flow's informational `Channel label`.
- **M20** (non-idempotent retries): `flowTriggerReceive` and `appSubscriptionCreate` are retried only on a 429/THROTTLED, never on a 5xx that Shopify may already have processed; the sync sweep retries the Flow trigger later with backoff.
- **L40** (poison rows): backoff now grows from 1 minute to 6 hours; a row that exhausts its retries is logged as an error and counted on the Settings page with its last error.
- **L47** (customer block history): reads the customer's newest 100 orders, and logs lookup failures. Orders older than the `read_orders` 60-day window stay out of reach by design (`read_all_orders` is not requested).
- **I18/I14** (first-order preset, unrecorded facts): the Thank-you block now sends `isFirstOrder`, country and product ids with the answer and they are stored; the first-order preset writes only when `isFirstOrder` is true (unknown counts as no). The customer id is still never stored, by the privacy posture.
- **H20** (late `shop/redact`): skipped when the shop has reinstalled since the uninstall that triggered it (see the code-review refinement below), and a warning is logged. Deleting would wipe the merchant's current surveys, answers and live session.
- **M10** (late `app/uninstalled`): ignored when its `X-Shopify-Triggered-At` is earlier than the current installation's start (new nullable `Shop.installedAt`, additive migration seeded from `createdAt`). Without that header the uninstall still applies, as before.
- **H19/M11** (deferred redacts): the remainder of a large `customers/redact` drains in the background right after the webhook, every webhook kicks a throttled drain of all shops' queued redacts, and retention executes (never discards) queued redacts.
- **L28** (redacted orders come back): a new `RedactedOrder` tombstone table (additive migration) records every order a redact names; later order webhooks and answers for it are ignored (the buyer still sees "thanks"). Tombstones age out on the 24-month record clock.
- **L32** (`shop/redact` never arrives): retention deletes a shop uninstalled more than 30 days ago (sessions included) — well past Shopify's 48-hour redact, so it only acts when that delivery was lost.
- **L30** (daily stats after redact): `SurveyDailyStats` is cleared for the shop on a customer redact. Nothing reads the table, and a day bucket can describe a single order.
- **M12** (data request): `orders_requested` is now read; the full answers for those orders are stored in the data-request record and the Settings page lists which orders had answers.
- **H18/M13/M14** (billing notices out of order, test charges): every `app_subscriptions/update` for a known subscription is checked against Shopify's current `activeSubscriptions` before it is applied (an ACTIVE notice must still be active there; a non-active one is ignored while Shopify still reports it active), the test flag comes from that answer, and a non-active status is written with one conditional update on the stored subscription id. A failed lookup returns 500 so Shopify retries.
- **M15** (development stores): charges are created as test charges, and honoured, outside production *and* on a development store (`shop.plan.partnerDevelopment`, cached an hour), which can approve nothing else. A failed lookup counts as "not a development store".
- **L37** (two usage counters): the v2 counter now counts every answer like the legacy one (an atomic upsert), and an answer past the cap is flagged by its position; the shared `BillingUsage` row shows true volume.
- **I20** (locked answers after upgrade): moving to an active paid plan clears the over-cap flag on the shop's answers. Uninstall records Free as `cancelled` (the charge ended); Shopify's `ACCEPTED` maps to the pending status, not `expired`.
- **I21** (choosing the current plan): refused server-side ("already on this plan") instead of creating a duplicate charge; `replacementBehavior` is left at Shopify's default.
- **S1-2** (API version): pinned as `API_VERSION` in `app/lib/env.ts`; `SHOPIFY_API_VERSION` is optional and any other value refuses to boot. A test keeps the code, `shopify.app.toml` and every extension on the same version.
- **S1-4/S1-5** (config and docs): the ignored `scopes_api_version` key was removed; a boot warning fires when `SCOPES` differs from the declared scopes; the deployment and privacy docs now list the four scopes and the protected-customer-data review that `write_customers` brings.
- **L4** (key rotation): an optional `TOKEN_ENCRYPTION_KEY_PREVIOUS` is tried after the current key, and undecryptable-session logs name the session and shop. Adding a key id to the `enc:v1:` format was not needed for this.
- **I8** (`/readyz` sharing the retention secret): an optional `READYZ_SECRET` (header `x-readyz-secret`) separates them; without it the old header still works, so existing monitors keep working.
- **L5** (`/auth/login`): added the library's standard login route (a minimal shop-domain form outside the admin) instead of leaving the path to the `/auth/*` splat.
- **L7** (placeholder shop id): replaced on the next admin load once Shopify answers, at most one retry per shop per process.
- **Code review: client-supplied `surveyVersion`.** Not changed. A caller can send an old version to skip `required` checks, but anyone holding a checkout token can already submit any valid answers to every question, so it does not widen what a forger can do, and the per-token cap and shop backstop still bound volume.
- **Code review: global v2 recovery sweep.** Kept process-wide and hourly (`maybeMarkUnreconcilable`), the same design as the legacy `markUnreconcilable` sweep it runs beside; its join only touches rows with no total.
- **Code review: `shop/redact` and reinstalls (refines H20).** A redact is skipped only when the current installation began after the uninstall it follows (`installedAt` later than `X-Shopify-Triggered-At` minus 49 hours). A shop still marked installed only because our uninstall handling never ran is redacted as asked.

## Steps for the repository owner (not done here: deploys or touching real data)

1. **C1 — only if a production deploy already failed on `20261012095226_multi_question_survey`.** Run `npx prisma migrate status` against production. If that migration is listed as failed: check whether its tables exist (`\dt "Survey"`). If they do not, run `npx prisma migrate resolve --rolled-back 20261012095226_multi_question_survey` and redeploy. If they do (partial apply), they hold no merchant data (the backfill aborted); drop the nine new tables and two enums the migration creates, then resolve and redeploy. Take a Neon branch/snapshot first.

2. **C5 — existing template surveys created before this fix** have show-if conditions pointing at ids that were never stored (follow-ups never show; the Studio refuses to save with `show_if_unknown`). They are not rewritten automatically because that would change merchant data. To repair one, open it in the Studio and re-pick the follow-up's condition (or delete and recreate it from the template). A query to find them: `SELECT q."surveyId" FROM "Question" q WHERE q."showIf" IS NOT NULL AND NOT EXISTS (SELECT 1 FROM "Question" p WHERE p.id = (q."showIf"::jsonb->>'questionId'));`
3. **Deploy note:** this branch adds migration `20261015090000_template_keys` (two nullable columns, additive). `npm run start` applies it.
4. **Deploy note:** migration `20261015100000_order_triggered_at` adds one nullable column to `OrderCache` (additive). `npm run start` applies it.
5. **After deploying, run `shopify app deploy`** so the checkout and admin extensions ship (the admin blocks gained `locales/`, the Thank-you block sends order facts). Shopify then re-runs the extensions' review-free update; nothing else is required.
6. **Deploy note:** migration `20261015110000_install_time_and_redacted_orders` adds `Shop.installedAt` (seeded from `createdAt` for installed shops) and the `RedactedOrder` table. Additive; `npm run start` applies it.
7. **Optional hardening:** set `READYZ_SECRET` in Render and switch the `/readyz` monitor (if any) to send `x-readyz-secret`, so it no longer holds the secret that authorises `/jobs/retention`.

## 2026-10-20 audit

- **M6** (sync work deleted on a blip): a frozen Scale plan defers queued work (it backs off and retries); a shop actually on a lower plan settles it with nothing written. Sync reuses the token the sweep already fetched instead of fetching it again.
- **M7** (Flow re-sent after a 5xx/timeout): Flow is at most once. A failure after the trigger may have reached Shopify settles the row with an "outcome unknown" error log; only failures Shopify certainly refused are retried. A duplicate workflow run (discount email, alert) is worse for a merchant than one missed run, and Flow has no idempotency key.
- **H2** (resubmits re-queue work): completed sync rows are kept (`PendingSync.completedAt`) instead of deleted, so `enqueueSync` sees them; they age out with the 24-month record clock.
- **L28/L29** (order updates bypass backoff): sync waiting on an order is started only when the order is first stored (webhook or backfill), never by later updates.
- **L40** (customer block misses older answers): `read_all_orders` is still not requested (scope minimisation); the block now says it looked at the customer's recent orders (about 60 days) instead of "no answer recorded".
- **L41** (admin block shows the wrong answer): the block shows only the survey's channel-report question; a survey without one shows nothing rather than a gift/price/NPS answer labelled "How they heard about us".
- **L45** (sync only drains on admin visits): a failed row arms an in-process timer for its retry time. Nothing is scheduled when nothing failed, so an idle app still never wakes the database.
- **L48** (metafield conflicts): the reorder-window preset is written as `number_integer`; duplicate fields are dropped before the call and each owner gets its own call. The `sourcetrac` namespace stays merchant-owned (not `$app:`) because these metafields are meant for the merchant's own segments and Flow.
- **C2** (webhook auth refreshes tokens): webhooks are verified by the library's own `authenticate.webhook` on a second `shopifyApp` instance whose session storage holds nothing, so no session is loaded or refreshed before our handlers run. Hand-rolling HMAC was rejected (AGENTS.md); only `app_subscriptions/update` resolves a token, by itself (L22).
- **H1/M3** (reinstall vs late uninstall/redact): `Shop.authorizedAt` records every token grant (proof the app was installed then) and `Shop.uninstallTriggeredAt` keeps the latest uninstall time across reinstalls. A late `app/uninstalled` is ignored when a grant came after it; `shop/redact` is skipped when the last grant/install is after the recorded uninstall (the fixed 49-hour window is only the fallback when no uninstall was ever recorded).
- **L11** (redact vs concurrent order webhook): instead of a shared lock, an order webhook that *creates* a cache row re-checks the redaction tombstone after the insert and removes the row; the redact writes its tombstone before deleting, so every interleaving ends with no row.
- **L14** (deferred redacts after a restart): the server drains every queued redact once at boot in production (the database is already awake from the start-up migration), in addition to the existing webhook and dashboard sweeps.
- **L18** (data-request completeness): the stored export now also lists each named order's cached order data, first-order flag and recent checkout loads, and each answer's country, language, products and first-order flag.
- **H4** (backstop drained by forged ids): once the shop-wide backstop is empty, an order id the cache does not know is looked up in Shopify (`order(id:)`, read_orders) and let through if it exists; lookups are capped per shop (30 burst, one per 2s) and remembered (10 min real, 1 min unknown). Requests the server refuses as invalid now count against the token's 2-submission cap; only stored answers and server-side failures give the slot back.
- **L2** (retry loop): eight attempts, backoff 1s doubling to 16s with 50-100% jitter, each attempt capped at what is left of the 60s budget, and the eighth held back to the end of the budget so a full-minute cold start is still caught.
- **L5** (stale version waives required): new `Question.requiredSinceVersion` (additive migration); a buyer on an older version is excused only from questions that became required after it. Version 0 or any old number no longer waives every required question.
- **L6** (legacy single-question path): the v2 path's per-order advisory lock, the usage claim and the insert now run in one transaction there too, and the per-token slot is reserved/released like v2. Sync and admin-block display stay v2-only: no shipped block calls the legacy route (the app was never deployed with it), so building sync for it would add code for crafted requests only.
- **L7** (product/collection targeting never applied): such rules are dropped when a survey is saved, rather than implemented: no editor offers them, and the checkout never sends product ids with the config request. A saved survey therefore never claims a rule that does nothing.
- **I2** (merchant settings sent to buyers): `/api/survey` strips targeting, response count, rotation, priority, payment rule and channel question from the survey it serves; targeting is decided on the server.
- **I3** (preview route accepts buyer tokens): left as is. A checkout session token carries no claim that tells the checkout editor from a buyer's page, and the route only returns the merchant's own survey text (no answers); this is recorded rather than guessed at.
- **M2/L19** (refresh and migration races): token loads are de-duplicated per shop in the process, and the session storage never stores an offline session whose expiry is older than the stored one (a session without an expiry, a legacy token, counts as oldest). A migration first re-reads the row and uses an already-migrated session. Cross-process coordination is not added: the app runs as one instance.
- **L20** (legacy exchange retried on every load): a failed exchange waits 10 minutes (per process) before it is tried again; the session reads as absent meanwhile, as before.
- **L21** (key rotation): a token that only the previous key opens is re-sealed with the current key when its session is loaded, not only when it is next stored.
- **L23** (`/auth` provisioning): the route now uses `ensureShop` (no second identity call when the shop exists) and logs instead of failing a successful login.
- **L24** (changed myshopify domain): a row found by the shop's GID under another domain is moved to the new domain before the upsert, when no row holds the new domain yet.
